Every paid order of a seller's goods becomes a fulfillment task in the warehouse. The seller works the queue:
scan every line of a task, which starts packing it and, at the last line, packs the parcel and tells order; wait
until order has booked a courier and recorded the parcel's tracking number; then print the label. The warehouse
calls need a session whose role is `seller`
([Become a seller](/apis/rest/seller-web/become-a-seller/), step 5).

## 1. A paid order becomes a task

Tasks are not created over REST. Order's checkout saga creates one over gRPC once the buyer's payment is held in
escrow, with the order's number and its lines, each a SKU and a quantity
([CheckoutSagaRunner.cs](https://github.com/WildanFrananda/kinetix-order-service/blob/97118d2d78819ef98b74a21efb4ebc4c8247e4e8/Application/Checkout/CheckoutSagaRunner.cs#L237-L277)).
Its due time, `same_day_cutoff_at`, follows the merchant's cutoff hour
([Store set-up](/apis/rest/seller-web/store-setup/)).

## 2. Read the queue

The queue is the seller's work: tasks still to pack, and packed parcels whose label has not been printed. Keep
each task's `id`, which every later step takes, and its `lines`, which say what goes into the parcel, from which
bin, and whether a scan has matched each line yet (`scanned`).

<RestEndpoint id="warehouse.taskQueue" via="seller-web" />

## 3. Start packing

Moving a `received` task to `packing`, with its `id` from step 2, tells the warehouse the packer has started. The
step can be left out: the first matching scan in step 4 does the same. The same endpoint takes `packed` in step 5.

<RestEndpoint id="warehouse.setTaskStatus" via="seller-web" />

## 4. Scan the items

Send each code the packer scans, with the task's `id`, once for each line. A SKU marks its line as scanned, and the
first match moves a `received` task to `packing`. The scan that matches the last unscanned line packs the parcel
and tells order that it is ready, and order books a courier
([verify_scan_service.rb](https://github.com/WildanFrananda/kinetix-warehouse-service/blob/cc5ff5ff80b6342e2cafdb262f931e2e03dedf50/app/services/fulfillment/verify_scan_service.rb#L64-L98),
[task_transitions.rb](https://github.com/WildanFrananda/kinetix-warehouse-service/blob/cc5ff5ff80b6342e2cafdb262f931e2e03dedf50/app/services/fulfillment/task_transitions.rb#L28-L35)).
`lines_remaining` says how many lines are left. The order number or the tracking number matches too but marks no
line, and a scan of a task that is already `packed` changes nothing and tells order nothing. A code that matches
nothing moves nothing.

<RestEndpoint id="warehouse.verifyScan" via="seller-web" />

## 5. Re-send the packed report

A task becomes `packed` only once a scan has matched every line: on a `packing` task, step 3's endpoint refuses
`packed` while a line is still unscanned
([advance_task_service.rb](https://github.com/WildanFrananda/kinetix-warehouse-service/blob/cc5ff5ff80b6342e2cafdb262f931e2e03dedf50/app/services/fulfillment/advance_task_service.rb#L59-L62)).
Once the task is `packed`, sending `{"status": "packed"}` to that endpoint re-sends the report to order, and this
is what it is for: when the scan that packed the parcel answered `order_notified` `false` with order unreachable,
no courier has been booked yet
([advance_task_service.rb](https://github.com/WildanFrananda/kinetix-warehouse-service/blob/cc5ff5ff80b6342e2cafdb262f931e2e03dedf50/app/services/fulfillment/advance_task_service.rb#L93-L116)).
Order keeps one courier booking per order, so a report sent again books no second courier
([FulfillmentPackedHandler.cs](https://github.com/WildanFrananda/kinetix-order-service/blob/97118d2d78819ef98b74a21efb4ebc4c8247e4e8/Application/Fulfillment/FulfillmentPackedHandler.cs#L62-L81)).

## 6. Wait for the tracking number

Order asks matching for a courier for the parcel and receives the parcel's tracking number (AWB)
([CourierDispatcher.cs](https://github.com/WildanFrananda/kinetix-order-service/blob/97118d2d78819ef98b74a21efb4ebc4c8247e4e8/Application/Fulfillment/CourierDispatcher.cs#L72-L108)),
then records it in the warehouse over gRPC
([CourierDispatcher.cs](https://github.com/WildanFrananda/kinetix-order-service/blob/97118d2d78819ef98b74a21efb4ebc4c8247e4e8/Application/Fulfillment/CourierDispatcher.cs#L122-L151),
[fulfillment_task_service_handler.rb](https://github.com/WildanFrananda/kinetix-warehouse-service/blob/cc5ff5ff80b6342e2cafdb262f931e2e03dedf50/app/rpc/fulfillment_task_service_handler.rb#L74-L99)).
From then on, the task's card in the queue carries it as `tracking_number`
([task_queue_service.rb](https://github.com/WildanFrananda/kinetix-warehouse-service/blob/cc5ff5ff80b6342e2cafdb262f931e2e03dedf50/app/services/fulfillment/task_queue_service.rb#L54)).
Until then `tracking_number` is `null` and no label can be printed: read the queue again (step 2) until it is
set.

## 7. Print the label

With the task's `id`, once its `tracking_number` is set. `awb_number` is the tracking number the label carries.
After the first print the task leaves the queue; the seller finds it again by its order number
([Returns](/apis/rest/seller-web/returns/), step 1).
