Nobody signs up as a seller. An account is created as a `customer`, files an application to sell, and an admin
approves it in the backoffice; only then is the account a `seller`. The calls are a sign-up (or a sign-in, for an
account that already exists), the application, and reads of its status until the decision; the `seller` role then
reaches the session without a call of its own.

## 1. Create an account

The seller types an email and a password. The edge has identity create the account, which identity makes a
`customer` like every new account
([auth_usecase.service.ts](https://github.com/WildanFrananda/kinetix-identity-service/blob/e1540249863f47b42f5409abdc396c06aadbb1e7/src/application/services/auth_usecase.service.ts#L139-L154)),
and starts its session in the same answer, as a sign-in does
([sign_up.tl](https://github.com/WildanFrananda/kinetix-edge-service/blob/400b6e95f432defbf2b52a81ab3096d4b5cf77ca/src/http/sign_up.tl#L30-L49)).
A `201` is that session: the browser holds `__Host-kx_session`, and since a new account has no second factor, no
sign-in and no code follow. After `409` `EMAIL_TAKEN` the account exists already, and the application signs in
instead ([Sign in](/apis/rest/seller-web/sign-in/), steps 1 and 2). An account that already buys on Kinetix also
signs in rather than signing up, since the seller web admits a `customer`, and applies as it is. Either way the
application then reads the account (Sign in, step 4) and keeps `userId`, which steps 2 and 3 take as `id`.

<RestEndpoint id="edge.register" via="seller-web" />

## 2. File the application

Send the store's name, its business registration number, its tax id and its address as the seller enters them,
with `id` set to `userId`. The application then waits as `pending` for an admin.

<RestEndpoint id="identity.onboardSeller" via="seller-web" />

## 3. Follow the application

Read the application with the same `id` until `status` is no longer `pending`: `verified` goes on to step 5,
`rejected` to the end of step 4.

<RestEndpoint id="identity.getSellerApplication" via="seller-web" />

## 4. An admin decides

An admin reviews the pending applications in the backoffice and approves or rejects each one
([Seller applications](/apis/rest/backoffice/seller-applications/)). Approval makes the account's merchant
`verified`, sets the account's role to `seller` and marks the application `verified`; rejection only marks the
application `rejected`
([seller_onboarding_usecase.service.ts](https://github.com/WildanFrananda/kinetix-identity-service/blob/e1540249863f47b42f5409abdc396c06aadbb1e7/src/application/services/seller_onboarding_usecase.service.ts#L138-L206)).
After a rejection, the seller corrects the application and files it again with step 2, which puts it back to
`pending`, and step 3 follows it again.

## 5. The session takes the seller role

After the approval the session still says `customer`: an access token carries the role the account had when
identity issued it
([token.service.ts](https://github.com/WildanFrananda/kinetix-identity-service/blob/e1540249863f47b42f5409abdc396c06aadbb1e7/src/application/services/token.service.ts#L90-L104)),
and the edge keeps the role of the session's latest token. The edge renews the session's tokens on the first
`/bff/api/` call, or opening of the merchant socket, made once the access token has less than 60 seconds left
([session_use.tl](https://github.com/WildanFrananda/kinetix-edge-service/blob/400b6e95f432defbf2b52a81ab3096d4b5cf77ca/src/http/session_use.tl#L48-L55),
[timing.tl](https://github.com/WildanFrananda/kinetix-edge-service/blob/400b6e95f432defbf2b52a81ab3096d4b5cf77ca/config/timing.tl#L4)).
identity reads the role from the account for the new pair
([auth_usecase.service.ts](https://github.com/WildanFrananda/kinetix-identity-service/blob/e1540249863f47b42f5409abdc396c06aadbb1e7/src/application/services/auth_usecase.service.ts#L157-L210)),
and the edge stores it as the session's role
([sessions.tl](https://github.com/WildanFrananda/kinetix-edge-service/blob/400b6e95f432defbf2b52a81ab3096d4b5cf77ca/src/http/sessions.tl#L418-L432)).
identity's access tokens last 15 minutes (`expiresIn` 900), so an application that keeps calling `/bff/api/` has
the `seller` role within about 15 minutes of the approval, in `GET /bff/session`
([Sign in](/apis/rest/seller-web/sign-in/), step 3) as in every service. Until then the seller endpoints that read
the role from the token, those of warehouse, pricing and payment and catalog's list of the seller's own products,
answer `403`, and so does the merchant socket, with `SELLER_REQUIRED`
([Pack orders](/apis/rest/seller-web/packing/), step 2). Signing out and in again (Sign in, steps 5 and 1) starts a
session with the `seller` role at once. [Store set-up](/apis/rest/seller-web/store-setup/) comes next.
