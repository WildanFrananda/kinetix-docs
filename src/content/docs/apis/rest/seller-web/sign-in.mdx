The seller web application signs in through the edge on its own host, `seller.wildanfrananda.my.id`, never on
the API host. The browser holds no token: the edge keeps identity's token pair and gives the browser an
`HttpOnly` cookie, `__Host-kx_session`, which no script can read. Every other feature calls `/bff/api/<path>` on
the same host, and the edge sends the request on with the session's access token in `Authorization`
([forward_headers.tl](https://github.com/WildanFrananda/kinetix-edge-service/blob/eb13db007a21ca985ca33eca49e44dacf43e6354/src/http/forward_headers.tl#L27-L49)).
The page and the edge share one origin, so no call is a CORS request. The seller web admits accounts whose role is
`seller` or `customer`; a `customer` signs in here to apply to sell, and a `courier` or an `admin` is refused
([apps.tl](https://github.com/WildanFrananda/kinetix-edge-service/blob/eb13db007a21ca985ca33eca49e44dacf43e6354/config/apps.tl#L37-L51)).
The calls are a sign-in, the answer to a two-factor challenge when the account has one, a read of the session when
a page loads, a read of the account, and a sign-out.

What the browser sends with every call to the edge:

- The cookie. A `fetch` from the application's own page sends it without being asked, since a same-origin request
  carries the origin's cookies by default.
- `Origin` on every `POST`, `PUT`, `PATCH` and `DELETE`. The browser adds it, and the edge refuses the request
  unless it is exactly `https://seller.wildanfrananda.my.id`
  ([csrf.tl](https://github.com/WildanFrananda/kinetix-edge-service/blob/eb13db007a21ca985ca33eca49e44dacf43e6354/src/http/csrf.tl#L12-L30)).
- A body only as `application/json`, of at most 1 MiB. An HTML form or a `multipart/form-data` body does not pass
  the edge
  ([router.tl](https://github.com/WildanFrananda/kinetix-edge-service/blob/eb13db007a21ca985ca33eca49e44dacf43e6354/src/http/router.tl#L161-L185),
  [nginx.conf](https://github.com/WildanFrananda/kinetix-edge-service/blob/eb13db007a21ca985ca33eca49e44dacf43e6354/nginx/nginx.conf#L39)).

There is no refresh call. A session ends 7 days after it was last used, and 30 days after sign-in at the latest
([lifetimes.tl](https://github.com/WildanFrananda/kinetix-edge-service/blob/eb13db007a21ca985ca33eca49e44dacf43e6354/config/lifetimes.tl#L6)).
Each `/bff/api/` call is a use that extends it, and so is opening the merchant socket
([Pack orders](/apis/rest/seller-web/packing/), step 2). When the session's access token has less than 60 seconds
left, the edge first renews the token pair at identity, once for all the requests of the session that arrive
meanwhile
([session_use.tl](https://github.com/WildanFrananda/kinetix-edge-service/blob/eb13db007a21ca985ca33eca49e44dacf43e6354/src/http/session_use.tl#L22-L70),
[timing.tl](https://github.com/WildanFrananda/kinetix-edge-service/blob/eb13db007a21ca985ca33eca49e44dacf43e6354/config/timing.tl#L4),
[sessions.tl](https://github.com/WildanFrananda/kinetix-edge-service/blob/eb13db007a21ca985ca33eca49e44dacf43e6354/src/http/sessions.tl#L492-L513)).
Once the session has ended, by its limits, a sign-out, a newer sign-in or sign-up in the same browser or a renewal
identity refused, a `/bff/api/` call answers `401` `SESSION_ENDED` and expires the cookie; a browser without the
cookie gets `401` `SESSION_REQUIRED`. Either way the application shows the sign-in (step 1). A renewal that finds
the account is no longer a `seller` or a `customer`, such as a customer approved as a courier, ends the session with
`403` `ROLE_REFUSED`. These answers are listed with [the edge's answers](/apis/rest/#the-edges-answers).

## 1. Sign in with email and password

The seller types an email and a password. A `200` with `authenticated: true` is a session: the answer sets
`__Host-kx_session`, and its `role` and `principalId` are those step 3 answers later. A `role` of `customer` means
the account has not been approved to sell yet, and the application leads it to
[Become a seller](/apis/rest/seller-web/become-a-seller/). A `200` with `mfaRequired: true` is not a session yet:
the challenge waits in the edge behind a second cookie, `__Host-kx_pending`, for step 2 in this browser. After a
`429` `SIGN_IN_DELAYED`, the application waits the seconds in `Retry-After` before the next attempt; the delay
belongs to the account, whichever browser tries. A seller without an account creates one instead
([Become a seller](/apis/rest/seller-web/become-a-seller/), step 1), which starts the session without this step.

## 2. Answer the two-factor challenge

Only after a `200` with `mfaRequired`, from the same browser, which sends `__Host-kx_pending` by itself, within its
300 seconds. The seller types the six digits the authenticator app shows. A `200` is the session, as in step 1.
`CODE_REFUSED` means identity refused that code and kept the challenge: the pending sign-in stays, and the seller
types the code the authenticator shows now. `SIGN_IN_REQUIRED` means there is no challenge left to answer, because
its time ran out or identity ended it, after five refused codes for instance; the edge has dropped the pending
sign-in, and the sign-in starts again at step 1
([sign_in.tl](https://github.com/WildanFrananda/kinetix-edge-service/blob/eb13db007a21ca985ca33eca49e44dacf43e6354/src/http/sign_in.tl#L228-L251)).
An account gets a challenge once its seller has turned on
[two-factor authentication](/apis/rest/seller-web/two-factor/).

<RestEndpoint id="edge.verifyTwoFactor" via="seller-web" />

## 3. Read the session when a page loads

Before it shows anything else, the application asks the edge whether this browser is signed in.
`authenticated: false` shows the sign-in (step 1). Otherwise `role` decides what the application offers, the seller's features or
only the application to sell, and `principalId` is the id the other services know the seller by, such as review
([Earnings and reviews](/apis/rest/seller-web/earnings-and-reviews/)). Reading the session is not a use: it neither
extends the session nor renews its tokens, so a role granted since sign-in shows here only after a `/bff/api/`
call has renewed them ([Become a seller](/apis/rest/seller-web/become-a-seller/), step 5).

<RestEndpoint id="edge.session" via="seller-web" />

## 4. Read the account

When the application needs the account itself, it reads it through the edge. `userId` is the account id that
identity's own paths take as `{id}`: the application to sell ([Become a seller](/apis/rest/seller-web/become-a-seller/))
and [two-factor authentication](/apis/rest/seller-web/two-factor/). `expiresAt` here is when the session's current
access token expires, which the edge renews by itself; when the session ends is step 3's `expiresAt`.

<RestEndpoint id="identity.me" via="seller-web" />

## 5. Sign out

The application sends the request without a body. The edge ends the session at identity, deletes it and expires
both cookies; the account's sessions on other browsers and devices stay
([logout.tl](https://github.com/WildanFrananda/kinetix-edge-service/blob/eb13db007a21ca985ca33eca49e44dacf43e6354/src/http/logout.tl#L76-L105),
[identity_client.tl](https://github.com/WildanFrananda/kinetix-edge-service/blob/eb13db007a21ca985ca33eca49e44dacf43e6354/src/adapters/identity_client.tl#L75-L79)).
For a live session the `204` comes only once identity has ended it, and it also comes when there was nothing to
end, so a sign-out can be sent again. After a `503` or a `502` the session is kept and the browser is still
signed in: the application tries again later.
