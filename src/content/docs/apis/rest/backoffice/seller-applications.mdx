An account applies to sell from the seller web application with `POST /api/v1/sellers/{id}/onboard`
([Become a seller](/apis/rest/seller-web/become-a-seller/)), and the application waits in identity as `pending` until
an admin decides on it. The decision is what lets a seller trade: catalog and pricing ask identity about the seller's
merchant before accepting a product or a promotion
([product_service.py](https://github.com/WildanFrananda/kinetix-catalog-service/blob/ab557c90cb3230221c5a504def11fa7df26a6f7a/core/application/services/product_service.py#L148-L159),
[promotion_service.rs](https://github.com/WildanFrananda/kinetix-pricing-service/blob/0ed7db4cd6fb8d40375cab26dd7ac56ebce16a8a/src/services/promotion_service.rs#L43-L51)),
and identity permits a merchant to trade only once its store is `verified` or `active`
([merchant_standing.ts](https://github.com/WildanFrananda/kinetix-identity-service/blob/e1540249863f47b42f5409abdc396c06aadbb1e7/src/domain/merchant_standing.ts#L1-L5),
[identity_grpc.controller.ts](https://github.com/WildanFrananda/kinetix-identity-service/blob/e1540249863f47b42f5409abdc396c06aadbb1e7/src/adapters/controllers/identity_grpc.controller.ts#L237-L258)).
An admin, signed in from Kinetix's staff network as on [Sign in](/apis/rest/backoffice/sign-in/), lists the pending
applications, reads one and, if needed, the applicant's profile, then approves or refuses it. Identity records every one
of these calls with the admin who made it.

## 1. List the pending applications

Ask for `status=pending` to see the applications that wait for a decision; leave `status` out to see every one,
decided ones included. Each application names its applicant twice: by `userId`, the account id every later step takes
as its `id`, and by `principalId`, the principal the other services know the seller by, such as the
`merchant_principal_id` of its products in catalog and of its stock in warehouse
([Stock intake](/apis/rest/backoffice/stock-intake/)). Applications come oldest first, a page at a time: while
`nextAfterId` is a number, ask again with `after` set to it.

<RestEndpoint id="identity.listSellerApplications" via="backoffice" />

## 2. Read one application

Read the application of one applicant, with `id` set to the `userId` from step 1, to see it as it stands now rather
than as the list showed it. Steps 4 and 5 accept only an application whose `status` is still `pending`.

<RestEndpoint id="identity.getSellerApplication" via="backoffice" />

## 3. Read the applicant's profile

This step is optional. The application holds the store's details; the applicant's own name and phone number are in
the account's profile, which an admin may read for any account, again with `id` set to `userId`. For an applicant who
never saved a profile the answer is `404`, which says nothing about the application.

<RestEndpoint id="identity.getProfile" via="backoffice" />

## 4. Approve the application

Approving, with `id` set to `userId`, makes the account a seller and its store `verified`, from which moment the
merchant may trade. The seller's tokens carry the new role only from their next renewal: on the seller web the edge
renews them by itself, and signing out and in again gets the role at once
([the seller web's sign-in](/apis/rest/seller-web/sign-in/)). A `409` saying that another request wrote the store
at the same moment changed nothing; send the approval again. An account that became a courier or an admin after
applying cannot be approved: its `409` leaves the application `pending`, for step 5.

<RestEndpoint id="identity.verifySeller" via="backoffice" />

## 5. Refuse the application

Refusing instead of approving, with the same `id`, marks the application `rejected`. The account keeps its role and
may file a corrected application from the seller web application.

<RestEndpoint id="identity.rejectSeller" via="backoffice" />
