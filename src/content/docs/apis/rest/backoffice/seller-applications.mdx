An account applies to sell from the seller web application with `POST /api/v1/sellers/{id}/onboard`, and the
application waits in identity as `pending` until an admin decides on it. The decision is what lets a seller trade:
catalog and pricing ask identity about the seller's merchant before accepting a product or a promotion
([product_service.py](https://github.com/WildanFrananda/kinetix-catalog-service/blob/95cabdb917607026a290b7d24e91b7121a0631d3/core/application/services/product_service.py#L127-L138),
[promotion_service.rs](https://github.com/WildanFrananda/kinetix-pricing-service/blob/d3020a29ca7ac6fcc2d5a7e472a6b234cc783d0d/src/services/promotion_service.rs#L43-L51)),
and identity permits a merchant to trade only once its store is `verified` or `active`
([merchant_standing.ts](https://github.com/WildanFrananda/kinetix-identity-service/blob/4b8eb5e5f70f05a8a5f9b6bd0d04b2bf88cc8b7f/src/domain/merchant_standing.ts#L1-L5),
[identity_grpc.controller.ts](https://github.com/WildanFrananda/kinetix-identity-service/blob/4b8eb5e5f70f05a8a5f9b6bd0d04b2bf88cc8b7f/src/adapters/controllers/identity_grpc.controller.ts#L237-L258)).
An admin, signed in as on [Sign in](/apis/rest/backoffice/sign-in/), lists the pending applications, reads one and,
if needed, the applicant's profile, then approves or refuses it.

## 1. List the pending applications

Ask for `status=pending` to see the applications that wait for a decision; leave `status` out to see every one,
decided ones included. Each application names its applicant by `userId`, which every later step takes as its `id`.
Applications come oldest first, a page at a time: while `nextAfterId` is a number, ask again with `after` set to it.

<RestEndpoint id="identity.listSellerApplications" />

## 2. Read one application

Read the application of one applicant, with `id` set to the `userId` from step 1, to see it as it stands now rather
than as the list showed it. Steps 4 and 5 accept only an application whose `status` is still `pending`.

<RestEndpoint id="identity.getSellerApplication" />

## 3. Read the applicant's profile

This step is optional. The application holds the store's details; the applicant's own name and phone number are in
the account's profile, which an admin may read for any account, again with `id` set to `userId`. For an applicant who
never saved a profile the answer is `404`, which says nothing about the application.

<RestEndpoint id="identity.getProfile" />

## 4. Approve the application

Approving, with `id` set to `userId`, makes the account a seller and its store `verified`, from which moment the
merchant may trade. The seller's tokens carry the new role only after its next refresh or sign-in. A `409` saying that
another request wrote the store at the same moment changed nothing; send the approval again.

<RestEndpoint id="identity.verifySeller" />

## 5. Refuse the application

Refusing instead of approving, with the same `id`, marks the application `rejected`. The account keeps its role and
may file a corrected application from the seller web application.

<RestEndpoint id="identity.rejectSeller" />
