Order runs each checkout as a saga across pricing, warehouse and payment, and keeps a delivered order open until its
return window closes, when it completes and pays the merchant. A few cases wait on a person: a saga that could not
unwind on its own, a return a merchant opened, an order staff decide to complete early. Signed in at one of the
backoffice's two addresses as on [Sign in](/apis/rest/backoffice/sign-in/), the admin counts and lists the sagas, lists
the returns, rejects a return or completes an order, searches the orders, and reads one. Order checks the token itself
on every endpoint here. It writes every call of steps 1 to 6, and an admin's read of an order the admin did not place,
to its audit log of admin actions
([AdminAudit.cs](https://github.com/WildanFrananda/kinetix-order-service/blob/a0167a3ec43e857e85401924b4bee486e596d4fd/Infrastructure/Observability/AdminAudit.cs#L30-L42)).

## 1. Count the sagas that need attention

A bare number, for a badge in the backoffice; step 2 lists the sagas behind it.

## 2. List the sagas that need attention

Each saga names its order by `orderNumber`, and each entry of its `unreleasedSteps` carries a `remedy` naming the gRPC
operation that gives the step back
([SagaAdminController.cs](https://github.com/WildanFrananda/kinetix-order-service/blob/a0167a3ec43e857e85401924b4bee486e596d4fd/Controllers/SagaAdminController.cs#L121-L137);
the operations are in the [gRPC reference](/apis/grpc/)). Order's REST API only reads sagas: this controller serves
these two `GET`s and nothing else
([SagaAdminController.cs](https://github.com/WildanFrananda/kinetix-order-service/blob/a0167a3ec43e857e85401924b4bee486e596d4fd/Controllers/SagaAdminController.cs#L12-L53)).

<RestEndpoint id="order.listSagasNeedingAttention" via="backoffice" />

## 3. List the returns that need attention

The returns still `OPEN`, and those whose goods came back but whose refund stopped. Keep each one's `returnNumber` for
step 4 and its `orderNumber` for step 5, or for step 6 to find its order.

<RestEndpoint id="order.listReturnsNeedingAttention" via="backoffice" />

## 4. Reject a return

Only an `OPEN` return whose goods have not come back can be rejected, with its `returnNumber` from step 3 in the path
and a `reason` in the body. The buyer then gets no refund, and the order completes when its return window closes, or
earlier through step 5. After a `500` or a `503`, whose outcome is unknown, the rejection can be sent again: a return
the first attempt rejected answers `409` `RETURN_ALREADY_REJECTED` and nothing changes.

<RestEndpoint id="order.rejectReturn" via="backoffice" />

## 5. Complete an order early

Complete a `DELIVERED` order by its `orderNumber`, from step 3 or elsewhere, instead of waiting for its return window
to close. A return against the order that is `OPEN` or `GOODS_RECEIVED` blocks this with `409` `RETURN_UNRESOLVED`;
an `OPEN` one can be rejected in step 4 first, if that is the decision. A `200` means the order is `COMPLETED`, so the
call is not repeated for it. `escrowReleased` says whether payment released the escrow to the merchant at once; when
it did not, `detail` is one of two fixed sentences, which the backoffice can map to its own words: payment could not be
reached and order retries the release on its own, or payment refused and the release waits for staff
([OrderCompletion.cs](https://github.com/WildanFrananda/kinetix-order-service/blob/a0167a3ec43e857e85401924b4bee486e596d4fd/Application/Completion/OrderCompletion.cs#L21-L25),
[OrderCompletion.cs](https://github.com/WildanFrananda/kinetix-order-service/blob/a0167a3ec43e857e85401924b4bee486e596d4fd/Application/Completion/OrderCompletion.cs#L175-L178)).
After a `500` or a `503`, whose outcome is unknown, the call can be sent again: an order the first attempt completed
answers `409` `ORDER_ALREADY_COMPLETED` and nothing changes.

<RestEndpoint id="order.completeOrder" via="backoffice" />

## 6. Search the orders

Every order, newest first, a page at a time: by status, by when it was created, by its merchant or its buyer, or by its
`orderNumber`, such as one from step 3 or one a buyer quotes. The filters given all apply together. Each order on a page
is a summary with its `id` and no address, recipient or phone; step 7 reads those, one order at a time. A filter order
cannot read exactly is refused with `400` naming the `parameter`, never answered with a page, because a filter left out
quietly would answer a wider list that looks like the true one
([OrderSearchParameters.cs](https://github.com/WildanFrananda/kinetix-order-service/blob/a0167a3ec43e857e85401924b4bee486e596d4fd/Application/Search/OrderSearchParameters.cs#L53-L106)).
For the next page, send the answer's `nextCursor` as `before` with the same filters; the last page answers
`nextCursor: null`. Each search is written to the audit log with the names of its filters and never their values, so the
log does not become a second record of who bought from whom
([OrderSearchController.cs](https://github.com/WildanFrananda/kinetix-order-service/blob/a0167a3ec43e857e85401924b4bee486e596d4fd/Controllers/OrderSearchController.cs#L19-L41)).

<RestEndpoint id="order.searchOrders" via="backoffice" />

## 7. Read an order

An admin reads any order, but only by its `id`, the UUID that the buyer's checkout answer and order list carry, and
each order of the search in step 6. The sagas and the returns above name orders by `orderNumber` alone, and the path
takes only a UUID
([OrderController.cs](https://github.com/WildanFrananda/kinetix-order-service/blob/a0167a3ec43e857e85401924b4bee486e596d4fd/Controllers/OrderController.cs#L344-L374)):
to read an order known by its number, find its `id` with `orderNumber` in step 6.
`GET /api/v1/orders/my-orders` lists only the caller's own purchases
([OrderController.cs](https://github.com/WildanFrananda/kinetix-order-service/blob/a0167a3ec43e857e85401924b4bee486e596d4fd/Controllers/OrderController.cs#L293-L342)).
