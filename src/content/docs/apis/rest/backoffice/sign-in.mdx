The backoffice is the web application the API expects Kinetix staff to use. It has no public host: staff open it at
an address that is not published, a Tor onion service that connects only a browser holding a client key or, when Tor
is unavailable, an address on Kinetix's staff network, so this reference writes its origin `<backoffice origin>`. It
never holds a token. The browser calls only its own origin, under `/bff/`, where the edge keeps the session, a
separate one at each of the two addresses: it signs the admin in with identity, keeps the token pair, adds the access
token to every `/bff/api/` call it passes on to the API, and renews the pair by itself when a call finds the access
token under a minute from expiry
([timing.tl](https://github.com/WildanFrananda/kinetix-edge-service/blob/400b6e95f432defbf2b52a81ab3096d4b5cf77ca/config/timing.tl#L4)).
The browser holds only the `HttpOnly` cookie `__Host-kx_session`, which page scripts cannot read and the browser sends
back by itself, so this page has no refresh step. What every call through the edge sends and gets back is in
[The edge](/apis/rest/#the-edge).

The backoffice admits only accounts whose `role` is `admin`, and only with a second factor: an admin who has none is
led through enrolling one before any session starts. It offers no sign-up: the edge's `POST /bff/register` belongs to
the seller web and answers `404` here. The staff-network address answers only from Kinetix's staff network; from
anywhere else Kong refuses every request there, sign-in included, with `403`
([Kong's answers](/apis/rest/#kongs-answers)).

## 1. Look for a session

On every page load, before showing the sign-in form, ask the edge whether this browser is signed in.
`authenticated: true` means the app can be shown: `role` is `admin`, and `expiresAt` is when the session ends if the
admin does nothing. `authenticated: false` means step 2. Reading the session is not a use of it, so calling this
again and again keeps nothing alive.

<RestEndpoint id="edge.session" via="backoffice" />

## 2. Sign in with email and password

The email and the password the admin types go to the edge, which asks identity. On the backoffice a password alone
never starts a session, so a `200` carries one of two flags, and with either the edge sets the `HttpOnly` cookie
`__Host-kx_pending`, which holds the sign-in in progress:

- `mfaRequired`: the account has a second factor. Go to step 3 within 300 seconds, in the same browser.
- `mfaEnrolmentRequired`: the account is an admin without a second factor. Go to steps 4 and 5 within 600 seconds,
  then sign in here again.

A `403` `ROLE_REFUSED`, here or in step 3, means the account is not an admin and cannot use the backoffice; the edge
has already signed its tokens out at identity. After a `429`, wait the seconds in `Retry-After` before the next
attempt.

<RestEndpoint id="edge.login" via="backoffice" />

## 3. Answer the two-factor challenge

After `mfaRequired`, send the six digits the admin's authenticator app shows; the browser sends `__Host-kx_pending`
from step 2 by itself. A `200` starts the session: the edge sets `__Host-kx_session`, expires the pending cookie, and
answers the same view as step 1.

The session ends after 15 minutes without a `/bff/api/` call, or 8 hours after this step, whichever comes first
([lifetimes.tl](https://github.com/WildanFrananda/kinetix-edge-service/blob/400b6e95f432defbf2b52a81ab3096d4b5cf77ca/config/lifetimes.tl#L5)),
and its cookie has no `Max-Age`, so it also ends when the browser closes
([apps.tl](https://github.com/WildanFrananda/kinetix-edge-service/blob/400b6e95f432defbf2b52a81ab3096d4b5cf77ca/config/apps.tl#L19-L35),
[lifetimes.tl](https://github.com/WildanFrananda/kinetix-edge-service/blob/400b6e95f432defbf2b52a81ab3096d4b5cf77ca/src/http/lifetimes.tl#L38-L44)).
After that, every `/bff/api/` call answers `401` `SESSION_ENDED`, and the admin signs in again at step 2. If the
account stops being an admin, the edge's next renewal of the tokens ends the session with `403` `ROLE_REFUSED`.

On `401` `CODE_REFUSED` the code was wrong and the sign-in is still pending: ask for the next code. identity allows
five codes per challenge
([sign_in_attempt_policy.ts](https://github.com/WildanFrananda/kinetix-identity-service/blob/e1540249863f47b42f5409abdc396c06aadbb1e7/src/domain/sign_in_attempt_policy.ts#L7)),
so after the fifth refusal the next code answers `401` `SIGN_IN_REQUIRED`. That answer means there is no pending
sign-in any more: its 300 seconds have passed, it was answered from another tab, or identity has ended the challenge,
and the edge has dropped it and expired `__Host-kx_pending`
([sign_in.tl](https://github.com/WildanFrananda/kinetix-edge-service/blob/400b6e95f432defbf2b52a81ab3096d4b5cf77ca/src/http/sign_in.tl#L243-L250)).
Go back to step 2, and in step 3 send the code the authenticator shows next.

<RestEndpoint id="edge.verifyTwoFactor" via="backoffice" />

## 4. Enrol a second factor: get a secret

Only after `mfaEnrolmentRequired` in step 2. The request has no body: the pending cookie names the enrolment. Show
`qrCodeUrl` as a QR code for the admin's authenticator app, and `twoFactorSecret` for typing in by hand. Calling this
again replaces the secret, so only codes from the latest one pass step 5. A `409` means the account got a second
factor through another sign-in meanwhile: go back to step 2, which now answers `mfaRequired`. A `401`
`SIGN_IN_REQUIRED` means the enrolment has ended, for instance because its 600 seconds have passed: start again at
step 2.

<RestEndpoint id="edge.setupTwoFactor" via="backoffice" />

## 5. Enrol a second factor: confirm a code

Send a code the authenticator app shows for the secret from step 4. A `200` turns two-factor authentication on but
starts no session: identity ends every session the account had and spends the enrolment, and the edge expires
`__Host-kx_pending`. Go back to step 2: the sign-in now answers `mfaRequired`, and step 3 starts the session. On
`401` `CODE_REFUSED`, send the next code; on `401` `SIGN_IN_REQUIRED`, the enrolment has ended as in step 4, so start
again at step 2.

<RestEndpoint id="edge.enableTwoFactor" via="backoffice" />

## 6. Read the signed-in account

This step is optional. Step 1 names the session's `role` and `principalId` but not the account's `email` or its
`userId`; this call does, passed on by the edge to identity with the session's access token. Its `expiresAt` is that
access token's, which the edge renews by itself: the session's own end is the `expiresAt` of step 1. Unlike step 1,
this call is a use of the session and moves its idle end later.

<RestEndpoint id="identity.me" via="backoffice" />

## 7. Sign out

The edge ends the session at identity and in its own store, and expires both cookies. The request has no body and is
safe to repeat, so it can be sent whatever step 1 last answered. After the `204`, show the sign-in form. A `503` or a
`502` means identity has not ended the session and the admin is still signed in: send the sign-out again later.

<RestEndpoint id="edge.logout" via="backoffice" />
