The notification service sends pushes for a principal to the handsets registered for it
([DeviceRegistryRecipientDirectory.scala](https://github.com/WildanFrananda/kinetix-notification-service/blob/4ad78ee085f9cc6b1bd055cf8e90fbefef97ff5e/src/main/scala/com/kinetix/notification/infrastructure/grpc/DeviceRegistryRecipientDirectory.scala#L11-L14)),
through Firebase Cloud Messaging (FCM). A buyer app gets the handset's FCM token (step 1) and registers it
with the buyer's access token (step 2). Some registrations are answered `202`: the handset then receives a
code by push (step 3) and sends it back (step 4). At sign-out the app forgets the handset (step 5).
`platform` takes only `ANDROID` or `IOS`, so these calls are for a mobile app.

## 1. Get the FCM token

The Firebase SDK on the handset issues the token; this is not an API call. The notification service
addresses each push to that token, as an FCM message with a title and a body
([HttpPushSender.scala](https://github.com/WildanFrananda/kinetix-notification-service/blob/4ad78ee085f9cc6b1bd055cf8e90fbefef97ff5e/src/main/scala/com/kinetix/notification/infrastructure/http/HttpPushSender.scala#L35-L40),
[the message](https://github.com/WildanFrananda/kinetix-notification-service/blob/4ad78ee085f9cc6b1bd055cf8e90fbefef97ff5e/src/main/scala/com/kinetix/notification/infrastructure/http/HttpPushSender.scala#L63-L72)).
When the SDK replaces the token, the app registers the new one (step 2) and forgets the old one (step 5).

## 2. Register the handset

`device_token` is the token from step 1, and `platform` the handset's system. The app registers at every
start and whenever the token changes; registering a token the buyer already holds only refreshes it. A `200`
is done. A `202` means another principal holds the token, and the handset must first prove that it receives
pushes sent to it: the app waits for step 3.

Only one proof at a time goes to a claimant, and a token gets at most three an hour, whoever claims it
([RegisterDevice.scala](https://github.com/WildanFrananda/kinetix-notification-service/blob/4ad78ee085f9cc6b1bd055cf8e90fbefef97ff5e/src/main/scala/com/kinetix/notification/application/RegisterDevice.scala#L42-L59),
[DeviceChallenge.scala](https://github.com/WildanFrananda/kinetix-notification-service/blob/4ad78ee085f9cc6b1bd055cf8e90fbefef97ff5e/src/main/scala/com/kinetix/notification/domain/DeviceChallenge.scala#L21-L43)).
So a registration repeated while a proof is pending sends nothing and is answered
`429 VERIFICATION_ALREADY_PENDING`: the app goes on to step 4 with the nonce already sent, and registers again
after `Retry-After` only if that message never came. After `429 VERIFICATION_LIMIT_REACHED` it registers
again once `Retry-After` seconds have passed. `422 ADDRESS_GONE` means FCM no longer knows the token: the app
gets a fresh one from the SDK (step 1) and registers that. A `503 SENDER_UNAVAILABLE` is repeated later; a
`502 SENDER_REJECTED` is not repeated unchanged.

## 3. Receive the verification message

After a `202`, the handset receives an FCM data message rather than a visible notification: on Android a
high-priority data message, on iOS a background push. Its data carries three fields
([HttpPushSender.scala](https://github.com/WildanFrananda/kinetix-notification-service/blob/4ad78ee085f9cc6b1bd055cf8e90fbefef97ff5e/src/main/scala/com/kinetix/notification/infrastructure/http/HttpPushSender.scala#L74-L101)):

```json
{
  "kind": "DEVICE_VERIFICATION",
  "nonce": "Vq3tX8mK2pL7wR9cN4bY6hJ1sD5fG0aZ-eU_iO3kQ7w",
  "expires_at": "2026-10-22T03:25:00.481236Z"
}
```

The app's FCM message handler picks out `kind` `DEVICE_VERIFICATION` and passes `nonce` to step 4 before
`expires_at`. Since only one proof is pending for the buyer and this token at a time, the nonce received is
the one step 4 takes.

## 4. Prove the handset holds the token

The app sends the same `device_token` and the `nonce` exactly as received, with an access token of the same
buyer that registered in step 2. A `200` completes the registration. On `422 VERIFICATION_NOT_PENDING` the
app registers again (step 2) and waits for a new message.

<RestEndpoint id="notification.verifyDevice" />

## 5. Forget the handset

When the buyer signs out, the app forgets the handset first, while it still holds the access token this call
needs, and then signs out at identity
([Stay signed in and sign out](/apis/rest/buyer-app/stay-signed-in/#3-sign-out)). The same call forgets an old
token after the SDK has replaced it. The answer is the same whatever the token's state, so it is safe to
repeat.
