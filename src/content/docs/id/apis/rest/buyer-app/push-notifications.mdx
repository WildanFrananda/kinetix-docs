Service notification mengirim push untuk sebuah principal ke ponsel-ponsel yang terdaftar untuknya
([DeviceRegistryRecipientDirectory.scala](https://github.com/WildanFrananda/kinetix-notification-service/blob/4ad78ee085f9cc6b1bd055cf8e90fbefef97ff5e/src/main/scala/com/kinetix/notification/infrastructure/grpc/DeviceRegistryRecipientDirectory.scala#L11-L14)),
lewat Firebase Cloud Messaging (FCM). Aplikasi pembeli mengambil token FCM ponsel (langkah 1) dan
mendaftarkannya dengan access token pembeli (langkah 2). Sebagian pendaftaran dijawab `202`: ponsel lalu
menerima sebuah kode lewat push (langkah 3) dan mengirimnya kembali (langkah 4). Saat keluar, aplikasi
melupakan ponsel itu (langkah 5). `platform` hanya menerima `ANDROID` atau `IOS`, jadi panggilan-panggilan ini
untuk aplikasi mobile.

## 1. Mengambil token FCM

Firebase SDK di ponsel menerbitkan token-nya; ini bukan panggilan API. Service notification mengalamatkan
setiap push ke token itu, sebagai pesan FCM dengan judul dan isi
([HttpPushSender.scala](https://github.com/WildanFrananda/kinetix-notification-service/blob/4ad78ee085f9cc6b1bd055cf8e90fbefef97ff5e/src/main/scala/com/kinetix/notification/infrastructure/http/HttpPushSender.scala#L35-L40),
[pesannya](https://github.com/WildanFrananda/kinetix-notification-service/blob/4ad78ee085f9cc6b1bd055cf8e90fbefef97ff5e/src/main/scala/com/kinetix/notification/infrastructure/http/HttpPushSender.scala#L63-L72)).
Ketika SDK mengganti token-nya, aplikasi mendaftarkan yang baru (langkah 2) dan melupakan yang lama
(langkah 5).

## 2. Mendaftarkan ponsel

`device_token` adalah token dari langkah 1, dan `platform` sistem operasi ponsel itu. Aplikasi mendaftar setiap
kali dibuka dan setiap kali token-nya berubah; mendaftarkan token yang sudah dipegang pembeli hanya
memperbaruinya. `200` berarti selesai. `202` berarti principal lain memegang token itu, dan ponsel harus lebih
dulu membuktikan bahwa ia menerima push yang dikirim ke token itu: aplikasi menunggu langkah 3.

Hanya satu bukti dalam satu waktu yang dikirim untuk seorang pengklaim, dan sebuah token menerima paling
banyak tiga bukti per jam, siapa pun yang mengklaimnya
([RegisterDevice.scala](https://github.com/WildanFrananda/kinetix-notification-service/blob/4ad78ee085f9cc6b1bd055cf8e90fbefef97ff5e/src/main/scala/com/kinetix/notification/application/RegisterDevice.scala#L42-L59),
[DeviceChallenge.scala](https://github.com/WildanFrananda/kinetix-notification-service/blob/4ad78ee085f9cc6b1bd055cf8e90fbefef97ff5e/src/main/scala/com/kinetix/notification/domain/DeviceChallenge.scala#L21-L43)).
Jadi pendaftaran yang diulang selagi sebuah bukti masih tertunda tidak mengirim apa pun dan dijawab
`429 VERIFICATION_ALREADY_PENDING`: aplikasi lanjut ke langkah 4 dengan nonce yang sudah dikirim, dan mendaftar
lagi setelah `Retry-After` hanya bila pesan itu tidak pernah datang. Setelah `429 VERIFICATION_LIMIT_REACHED`,
aplikasi mendaftar lagi begitu `Retry-After` detik sudah lewat. `422 ADDRESS_GONE` berarti FCM tidak lagi
mengenal token itu: aplikasi mengambil token baru dari SDK (langkah 1) dan mendaftarkannya.
`503 SENDER_UNAVAILABLE` diulang nanti; `502 SENDER_REJECTED` tidak diulang tanpa perubahan.

## 3. Menerima pesan verifikasi

Setelah `202`, ponsel menerima data message FCM, bukan notifikasi yang terlihat: di Android berupa data
message berprioritas tinggi, di iOS berupa background push. Data-nya membawa tiga field
([HttpPushSender.scala](https://github.com/WildanFrananda/kinetix-notification-service/blob/4ad78ee085f9cc6b1bd055cf8e90fbefef97ff5e/src/main/scala/com/kinetix/notification/infrastructure/http/HttpPushSender.scala#L74-L101)):

```json
{
  "kind": "DEVICE_VERIFICATION",
  "nonce": "Vq3tX8mK2pL7wR9cN4bY6hJ1sD5fG0aZ-eU_iO3kQ7w",
  "expires_at": "2026-10-22T03:25:00.481236Z"
}
```

Handler pesan FCM di aplikasi memilih `kind` `DEVICE_VERIFICATION` dan meneruskan `nonce` ke langkah 4
sebelum `expires_at`. Karena hanya satu bukti yang tertunda untuk pembeli dan token ini dalam satu waktu, nonce
yang diterima adalah yang dipakai langkah 4.

## 4. Membuktikan ponsel memegang token

Aplikasi mengirim `device_token` yang sama dan `nonce` persis seperti diterima, dengan access token milik
pembeli yang sama yang mendaftar di langkah 2. `200` menuntaskan pendaftarannya. Pada
`422 VERIFICATION_NOT_PENDING`, aplikasi mendaftar lagi (langkah 2) dan menunggu pesan baru.

<RestEndpoint id="notification.verifyDevice" />

## 5. Melupakan ponsel

Ketika pembeli keluar, aplikasi melupakan ponsel itu lebih dulu, selagi masih memegang access token yang
dibutuhkan panggilan ini, lalu keluar di identity
([Tetap masuk dan keluar](/id/apis/rest/buyer-app/stay-signed-in/#3-keluar)). Panggilan yang sama melupakan
token lama setelah SDK menggantinya. Jawabannya sama apa pun keadaan token-nya, jadi aman diulang.
